# 原理说明

> 这份文档解释"为什么会出现这些症状"。看懂之后，你大概能自己判断问题出在哪一层。

---

## 桌面端是怎么"下载"文件的

很多人以为桌面端点下载 = 浏览器下载。**实际不是。**

ChatGPT Windows 桌面端是一个 **Chromium PWA 外壳**（`chrome.dll` + `chrome_pwa_launcher.exe`），界面是网页，但文件读写由**本机后端进程**完成。

于是有两条完全不同的路径：

| 路径 | 触发条件 | 实际发生的事 |
|---|---|---|
| **正常路径** | 后端能拿到文件 | 后端**直接把文件写进目标目录**，界面只显示"下载完成" |
| **异常路径** | 后端拿不到文件 | App 调用 `openExternal`，**用系统默认浏览器打开一个链接** |

关键证据：检查 Chromium 的下载数据库（`Default\History` 里的 `downloads` 表），**一次下载记录都没有**——即使成功下载过文件。

这说明：**成功下载根本不经过浏览器下载管理器。**

### 那"跳浏览器"是怎么回事

跳浏览器不是"下载失败后的兜底 UI"，而是**另一条代码路径**。

当 App 需要从服务器取文件（比如云端生成的文件）却取不到时，它不会干等着，而是把链接丢给浏览器。而浏览器里：

- 可能没登录 ChatGPT（桌面端的登录态和浏览器是分开的）
- 或者链接是带时效的一次性签名 URL，已经过期

所以出现"跳过去也下不来"。

**根因仍然是网络。** 网络好了，正常路径就走通了。

## 代理是怎么被读取的

桌面端有两套进程，读代理的方式不一样：

| 进程 | 读代理的方式 |
|---|---|
| **Chromium 界面** | 跟随 **Windows 系统代理**（注册表 `Internet Settings`）。它的配置里没有独立的代理设置 |
| **Rust 后端（codex.exe）** | ① 调用 `WinHttpGetIEProxyConfigForCurrentUser` 读系统代理 ② 读 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY` 环境变量 ③ 通过 `dotenvy` 加载 `.codex\.env` |

所以想让桌面端联网，有两条路，任选其一即可：

1. **开启 Windows 系统代理**（多数代理软件默认这么做）
2. 在 `.codex\.env` 里写代理变量：

```ini
HTTP_PROXY=http://127.0.0.1:端口
HTTPS_PROXY=http://127.0.0.1:端口
ALL_PROXY=http://127.0.0.1:端口
NO_PROXY=localhost,127.0.0.1,::1
```

### 为什么"直连不通"不一定是配置错误

如果你的网络环境本身无法直连 `chatgpt.com`（比如需要代理才能访问），那么：

- 直连失败 = **正常**
- 只有走代理成功才算对

判断方法：

```powershell
# 直连（预期失败）
curl.exe -I --noproxy "*" https://chatgpt.com

# 走代理（预期 200）
curl.exe -I --proxy http://127.0.0.1:12450 https://chatgpt.com
```

### TUN 模式和系统代理模式的区别

| 模式 | 特征 | 影响 |
|---|---|---|
| **TUN / 全局模式** | 会出现一块虚拟网卡，所有流量被接管 | 任何程序都不需要配代理 |
| **系统代理模式** | 只有一块真实网卡，靠注册表告诉程序"走代理" | 只认系统代理的程序能通；**只认环境变量的程序需要单独配** |

用 `Get-NetAdapter` 看有没有虚拟网卡，就能判断是哪种模式。

## 为什么"代理明明开着"还是不通

这是最容易被误判的一节。**"点开了代理"不等于"代理一直在通"。**

### 代理软件通常由两个进程组成

以常见的桌面代理客户端为例：

| 进程 | 作用 | 特点 |
|---|---|---|
| 界面 / 托盘进程 | 窗口、图标、设置面板 | 一直开着，你看到的就是它 |
| **引擎进程（core）** | 真正监听端口、转发流量 | **会单独重启** |

两个进程**生命周期不一样**。你切节点、改规则、更新订阅、或者引擎崩了自动拉起时，**界面毫发无损，引擎却重启了一次**。

重启那几秒：端口消失 → 所有正在进行的请求瞬间失败。

打个比方：店招牌灯一直亮着（界面），后厨却在换班关火（引擎）。你在门外看，店明明开着；但那几秒点的单，全部退单。

**这也解释了日志里那个 `after 1 ms`——1 毫秒就失败，不是路远，是压根没人接。**

### 两种完全不同的"坏法"

把报错按内容分类，会发现是两类：

| 类型 | 日志特征 | 真实含义 | 界面上看得出来吗 |
|---|---|---|---|
| **连不上** | `error sending request`、`after 1 ms`、`Transport channel closed` | 端口没了，引擎在重启 | ❌ 看不出来 |
| **超时** | `request timed out` | 端口在，**但节点不回话** | ❌ 看不出来 |

第二种尤其隐蔽：端口正常监听、请求也发出去了，**对面就是不响应**。原因可能是节点服务器挂了、被限速、IP 被目标站点阻断、线路拥塞。

**此时代理界面会一直显示"已连接"，看起来完全正常。**

### 一个真实的数据特征

某次排查中，331 条报错里有这样一段：

```
11-23 02:20    一分钟内 152 条报错
```

**一分钟 152 条，不可能是"断了一整天"，而是某一次引擎重启的瞬间，所有在途请求同时失败。**

对比一下：如果是持续断网，报错会均匀铺开在几小时里；而这里是一个尖峰。

> 判断技巧：看报错是**均匀分布**还是**尖峰聚集**。
> 尖峰 = 瞬时事件（重启、切换）；铺开 = 持续性问题（节点长期不可用）。

### 怎么自己确认（不依赖界面）

```powershell
curl.exe -I --proxy http://127.0.0.1:端口 https://chatgpt.com
```

三种结果，对应三种情况：

| 返回 | 含义 |
|---|---|
| `HTTP/1.1 200 Connection established` | **真的通** |
| 卡住不动，最后超时 | **节点问题**（界面在骗你） |
| 立刻报 `Could not connect` | **引擎没了**（端口没监听） |

### 所以健康检查要查两关

这也是 `codex-health.ps1` 的设计依据：

```
第一关：端口在监听吗？              → 抓"引擎重启 / 没启动"
第二关：真的发一个请求，能回来吗？   → 抓"节点不通"
```

**只查第一关是不够的**——节点挂了端口照样在。

两关都过，才算真的通。

另外脚本还会检查**持有端口的进程启动多久了**：如果不到 60 秒，会提示"引擎刚启动，可能有几秒空窗"。

## 沙箱为什么没有网络

Codex 在 Windows 上跑命令时，会把命令放进**受限沙箱**（restricted token + 能力 SID + 防火墙规则）。

实测现象（在沙箱内执行）：

```
HTTP_PROXY = [http://127.0.0.1:端口]   ← 变量确实在
DIRECT 访问 -> 000
走代理访问 -> 000                       ← 有变量也连不通
写 %TEMP%  -> 拒绝访问
```

**这不是故障，是产品设计。** 官方的诊断命令也会明确显示：

```
✓ sandbox   restricted fs + restricted network
```

而且**改配置没用**：试过 `sandbox_workspace_write.network_access=true`，依然连不通——因为隔离在防火墙规则层面，不是配置项能改的。

### 那需要联网的命令怎么办

走 App 的**授权/审批流程**，让命令在沙箱外执行。这是产品提供的正规通道。

**不要**为了这个去关沙箱、加防火墙放行规则或者用管理员权限硬跑——那是在拆安全机制。

## EFS 加密

EFS（Encrypting File System）是 Windows 的文件级加密，加密后的文件只有**当初加密的那个用户账户**能读。

### 什么情况下会遇到

极少数情况下，安装目录里的文件会被打上 EFS 属性（正常安装不会）。检查方法：

```powershell
(Get-Item "C:\路径\某个.exe" -Force).Attributes
# 如果结果里有 Encrypted，就是被加密了
```

### 要不要处理

**先别急着解密。** 判断顺序：

1. 程序能正常启动、能正常读文件 → **不需要处理**
2. 日志里出现 `Access is denied` / `os error 5` / `拒绝访问`，且指向安装目录 → 才需要考虑

真要处理也必须：

- 先备份
- 确认是哪个目录在报错，**只处理那个目录**
- **不要**对 `C:\Program Files\WindowsApps` 整个目录批量 `cipher /d`——那会破坏应用包

### 为什么可能出问题

EFS 解密依赖当前用户的密钥。如果程序以**不同的用户身份**运行（比如服务账户、另一个本地账户），就拿不到密钥，读文件会直接失败。

这也解释了为什么"文件明明在那儿，程序却说拒绝访问"。

## 为什么日志里全是"连不上"

看日志时容易误判：几百条 ERROR 看起来像很多不同的故障，其实往往只有一类。

排查方法：**按错误消息归类，而不是按条数看。**

真实案例中，331 条 ERROR 只归结为三类：

| 来源 | 含义 |
|---|---|
| MCP transport | 远端 MCP 服务连不上 |
| models manager | 模型列表拉不下来 |
| responses websocket | 响应流 WebSocket 连不上 |

**全都是"连不上 chatgpt.com"的三种表现形式。**

还有一个决定性的细节值得记住：如果错误信息里写着

```
Could not connect to server ... after 1 ms
```

**1 毫秒就失败**，说明不是网络慢、不是超时，而是**目标端口根本没在监听**——代理软件那一刻不在。

如果是超时（`timed out`，几秒到几十秒），才更可能是网络质量或节点问题。

---

## 一句话总结

```
代理不可用
   ↓
界面 + 后端 都连不上服务器
   ↓
各种超时、断开、重试（日志里那几百条 ERROR）
   ↓
取不到文件 → 退化成"用浏览器打开链接"
   ↓
浏览器没登录态 → 下载也失败
```

所以排查顺序永远是：**先确认代理，再看别的。**
